# Strategy B role boundaries and founder review control (2026-11-05)

The portable authority is [current workflow rules](current-workflow-rules.md). C1–C13 resolve older conflicting prose below; project-specific authorizations are never inherited.

## Execution contract

Every implementation task must have a written AOSDF Strategy B plan and its initial review verdict before implementation dispatch. A scope assignment may first dispatch plan-writing/review work; that is not permission to implement. Keep plan depth proportional: a small change gets a brief plan, not the full High-risk machinery. High-risk plans retain the existing independent reviewer requirement; do not downgrade risks or call same-session review independent.

The plan author/Strategy B Architect owns technical design; the Strategy B Reviewer checks it against affected real code/contracts and records APPROVED or REDLINED. Only APPROVED scope passes to the Implementor. The Validator runs the approved binary acceptance. Plan, review, implementation, validation and As-built remain the task's execution record, not separate task-status boards.

## Roles

- **Solution Architect:** divide and route tasks among thread coordinators; make ownership/dependencies explicit, prevent overlap/duplicate work, resolve assignment conflicts and keep threads moving. Preserve existing canonical tracker write ownership and reconcile reported evidence without a separate technical acceptance/review gate. Do not choose the worker's design, independently approve its implementation, rerun its suite or demand per-result architect permission. A real technical question is routed to the task's Strategy B design/review roles; a necessary additional review/revision is brought to the founder first.
- **Thread coordinator / Principal Engineer:** dispatch plan/review work, then the approved implementation scope; schedule disjoint ownership, route contracts and reconcile results. An approved plan is not reviewed again by the coordinator. Checking task identity, approved revision, owned paths, required verdict/evidence presence and result integrity is administrative reconciliation, not permission to reassess design or add tests. No routine coordinator rerun of already-recorded validation. Preserve substantive failures and report exact missing acceptance; do not claim a pass from missing evidence.
- **Implementor / Validator:** execute the approved plan and its agreed checks. Ordinary code/test corrections inside that approved scope are permitted under the existing correction limits. Do not change design, acceptance, scope or validation criteria to make work pass. Append factual As-built/evidence without treating that append as a plan revision.

## Founder approval for any additional review or plan revision

The initial Strategy B review is part of the normal task workflow and needs no extra permission beyond the task authorization. After that initial review, **any further review or plan revision requires the founder's explicit approval first**. This includes redline-driven amendments, post-approval amendments, delta reviews, added independent implementation reviews, coordinator cross-reviews and architecture re-review. Prior permission for a particular bounded extra review/revision remains valid; task authorization alone, silence, elapsed time, APPROVED WITH CONDITIONS or a coordinator/architect opinion is not permission for another cycle. Do not treat this policy update as retrospective permission for future cycles.

When necessary, pause only dependent work and ask the founder one concise question: task and current approved/reviewed revision; concrete defect/new fact; minimum proposed revision/review and affected acceptance; why execution cannot safely continue; exact approval requested. Show the concrete issue first. Do not implement an unresolved substantive defect or bypass security/validation while waiting. Continue unrelated authorized work with disjoint ownership.

Do not manufacture requests for optional polish. Record optional wording/cleanup separately and leave the approved plan alone. Do not request approval to continue a valid approved plan, append factual evidence, or fix an implementation bug without changing the plan. No mandatory extra implementation-review gate is added by this policy. If an older gate still calls for one and no specific founder authorization covers it, ask before starting it. Never run it automatically and ask afterward.

## Improve Strategy B at the source

The Solution Architect and Principal Engineer are authorized by this directive to add demonstrated missing planning/review checks directly to maintained Strategy B guidance/templates. This is process maintenance, not an extra review layer or permission to change an active approved plan. Keep improvements concise and reusable; include only checks applicable to the task. At minimum the initial plan/review must establish:

1. Actual current baseline and reusable implementation/tools, concrete objective/non-goals and one owner per changed surface; dependencies and cross-thread compatibility order before shared edits.
2. A bounded approach and exact affected contract: tenant/subject identities, null/case/canonicalization semantics, privilege/owner boundaries, clock/expiry, concurrency/locking/uncertainty and failure behavior where relevant.
3. Execution feasibility: permitted principal/environment/tooling, no secret copying or unauthorized shared writes, migration immutability/transaction/stop-on-error/default-ACL requirements when affected. Reuse existing isolation; avoid building general machinery for one task.
   For read/security plans, inspect the actual function result/schema shape before initial review. Classify exposed credential values, secret-store locators, hashes and public DNS/DKIM material separately; a name-only “secret/token” regex is a signal, not a complete data-exposure proof. Seed a representative synthetic tuple so empty result arrays cannot hide the output shape. Review the applicable allowed/excluded exposure against the stated capability, without reading real secrets.
4. Binary acceptance linked to the objective: positive, meaningful negative and relevant race/failure controls; distinguish required regressions from optional exploration. Define correction/stop limits, resource/time expectations and conditional workload guarantees; do not claim unconstrained runtime safety from bounded disposable tests.
   Source-digest consumers count as affected tests on ANY hashed-byte change, including comments/formatting; inventory pinned dependencies in the initial plan and refresh the expected digest only for an intentional compatible change, then run its dependent check. A semantic-only change analysis cannot reuse evidence for a byte-hash assertion.
5. Compatibility/handoff/rollback feasibility and explicit source/incorporation/tier/live boundaries. No hidden runtime activation or fabricated legacy correspondence.

A new general lesson is recorded in the maintained rule/template once, not duplicated as new per-task documents or extra approval checkpoints. A discovered defect affecting an already reviewed plan still follows the founder-approval rule above. Framework changes beyond these concise workflow instructions, such as executable automation, migrations, releases or product features, require their own authorized scope.

## Immediate application

Apply at the next safe message/task boundary. Do not restart active workers or reopen finished slices. Existing approved implementation/validation continues unchanged. Newly needed plan revisions or extra reviews must be requested before execution. Acknowledge once in the existing channel; do not create a new receipt system.

Speed and efficiency are explicit process goals: no duplicate plan review by Solution Architect/coordinator, no routine duplicate test runs, no endless amendments, no new process subsystem to comply. Security, tenant isolation, secrets, failed acceptance and live-operation authority remain hard boundaries. No commit, push, deployment, database apply, spend or automation rearm is authorized here.


## Execution efficiency — founder-approved optimizations

Founder explicitly approved these additions with “apply them” on2026-11-05. They extend the workflow above; they do not authorize revising an already reviewed plan or introducing another review cycle.

1. **Batch compatible changes before review.** One bounded plan may cover several related small changes with compatible dependencies, risk and disjoint/sequential write ownership. Review the whole selected scope once, then execute its approved steps without per-file/substep approval. Do not conceal unrelated scope, risks or live-operation gates inside a batch. Do not amend an existing reviewed plan to batch more work without the founder's approval.
2. **Reuse the task's worker session and isolation.** Keep one worker conversation and the same owned isolated setup through an active bounded task when the baseline, secret controls and concurrency ownership remain valid. Avoid fresh sessions, copied trees and baseline reconstruction per substep. Clean up once at the task boundary. Reconcile changed ownership/baseline or interrupted processes before reuse; never retain unsafe state or keep paid idle sessions alive while waiting on external input. Do not redesign isolation infrastructure to implement this instruction.
3. **Targeted development checks, one agreed integration pass.** During implementation run the checks relevant to the current change. Run the approved required integration/regression set once on the completed artifact. Rerun only checks affected by later changes, failures, flaky/invalid evidence or a relevant unresolved concern. Preserve explicitly approved multi-version, negative-control, mutation, concurrency and live-tier requirements; don't delete a required check to save time. If the current plan explicitly demands additional passes, changing it needs the founder's approval.
4. **Reuse unchanged evidence by revision.** Reuse recorded passing results for the same relevant source, dependency/configuration, environment and test scope. Verify those facts with the existing revision/digest record; do not rerun unrelated suites merely because of a handoff. Changed consumed dependencies, integration context or invalidated assumptions require affected checks. Disposable evidence never substitutes for tier-specific acceptance. Coordinator reconciliation is not another validation run.
5. **Short coordinator messages.** Lead with the completed deliverable, actual blocker (if any), and next action/owner. Put command details/digests in the existing plan As-built and required worker evidence. Show existing required status fields compactly without repeating history. No new report, evidence index, receipt format or status board is introduced.
6. **Time budget before approval.** State a task-specific planning/review/build/validation time estimate or budget, the bounded deliverable and the expected largest cost in the initial plan/assignment. Use existing timestamps and status fields; do not implement a new timer/dashboard. A budget is an escalation checkpoint, not permission to bypass correctness: when exceeded, report elapsed phase, concrete reason and smallest remaining step. Continue only unchanged authorized work; ask the founder before a necessary plan revision/additional review/scope expansion. For already approved active tasks, report existing elapsed phases at the next boundary without retroactively rewriting the plan.
7. **Finish the usable slice.** Finish the selected tested deliverable and actionable consumer handoff before starting optional cleanup or another supporting-framework task. Separate unrelated discoveries through existing gaps/ownership records. A defect that prevents the task's guarantee remains blocking; do not relabel failed acceptance as optional.

These optimizations are operational instructions, not added acceptance gates. Apply immediately where consistent with the active approved plan; otherwise request the smallest necessary change from the founder under the review-control rule. No new worker, review, implementation scope, mode/model change or live operation is authorized by this section.
