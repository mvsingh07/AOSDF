# Adopt the 3.6.0 framework in an existing project

This is a portable migration recipe against the accompanying source snapshot. It is not an instruction to replace project documents wholesale. A framework update and an existing-project migration are separate actions.

1. **Resolve and record the target.** Read its instructions, installed framework version, execution strategy, workflow authority and Git status. Record product-specific deviations and the existing task/claim/accepted-result state. Do not downgrade a newer installation or overwrite concurrent work.
2. **Verify source.** From the source framework root run `python3 upgrades/check_inventory.py`. This distribution carries the actual reusable source; do not substitute an older product-local copy.
3. **Review policy adoption.** Compare `reference/current-workflow-rules.md` and its referenced amendments with the target's installed `06_Execution_Plan/` policies. Preserve explicit product constraints, scope and permissions. Adopt source policy by reviewed merge; the founder/project authority resolves conflicts. Coordination remains opt-in with an explicit process Mode.
4. **Install roles and prompts.** Adapt reusable `agents/` into `05_AI_Agent_System/agents/`, `templates/prompt_templates/` into its `prompt_templates/`, and coordination templates into `coordination-threads/`. Rewrite source-relative links for their installed destinations. Use `prompts/setup_aosdf.md` for the complete setup contract. Choose topology, identities, ownership, model policy, environment and budgets as project inputs; create only empty initial records for new actors. Preserve existing actor state and accepted artifacts.
5. **Keep automation inactive.** Copy reusable code, schemas, tests and `*.example.json` only. Do not copy runtime directories, credentials, active wave files, personal profiles or authorization. Keep actual runner enablement as separate project implementation and acceptance. File observers and receivers remain separate and bounded.
6. **Adopt document authoring deliberately.** Install `tools/`, `reference/document_authoring.md`, `reference/schemas/document-metadata.schema.json`, document templates and author instructions per the setup guide. New projects use the empty `templates/document-metadata-legacy.json`. Existing projects need a reviewed exact legacy inventory; never substitute another project's baseline. Preserve existing bodies, IDs, dates and accepted evidence. Configure the MkDocs hook from `templates/project_docs_site/mkdocs.yml.template`. Do not bulk-migrate or delete historical documents as part of a tooling copy.
7. **Validate.** Run the relevant isolated automation, notification and metadata suites in CONTRIBUTING.md. Check installed links, document creation/validation and the target docs build against its own baseline. Confirm the migration did not activate runners or alter live claims. Validate MCP/editor integrations only if changed.
8. **Record the result locally.** Only after agreed acceptance passes, record the project's installed framework version, adapted files, remaining deviations and evidence in its own receipt. Partial/blocked work retains the previous accepted version. Reapplying verifies incorporation without redispatching completed work. A successful source distribution check never marks a project migrated.

Rollback uses the target's reviewed pre-migration snapshot and must not overwrite later accepted work. The private originating update history is not needed to follow this recipe and is not included as public installation evidence.
