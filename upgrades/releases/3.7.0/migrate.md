# Migrate an existing installation to the consolidated automation bundle

This recipe changes the reusable source and install layout. It does not move another project's active records automatically.

1. Verify the actual target and installed baseline. Read its instructions and current workflow authority; inspect Git state and record active owners, task/claim identities, pending rounds, accepted receipts, runtime processes and local customizations. Complete 3.6.0 prerequisites before adopting the full release.
2. Verify the public source with `python3 upgrades/check_inventory.py`. Review `source-adaptations.json` for included captures and deliberate selection of the existing coordination flow. Never substitute an older product-local AOSDF copy.
3. Choose a normal idle checkpoint for a project-specific move. Obtain its authority before pausing/stopping/restarting processes. Do not run two engines over the same state. Preserve all accepted evidence and claims; do not reset work merely to adopt a new path.
4. Install the complete public `automation/` folder as `05_AI_Agent_System/automation/`. The old `templates/coordination_threads/automation/` source maps to `automation/`; old role/alignment material maps to `automation/coordination-threads/`; old notifications map to `automation/file-signals/`. Adapt an existing project's corresponding paths deliberately. Update hooks, process commands, owner records, notification paths and digest consumers before any authorized restart; preserve their evidence and versioned replacements. Source inventory hashes do not authorize rewriting accepted project evidence.
5. Set `AOSDF_PROJECT_ROOT` explicitly to the adopting workspace. Install root roles into `05_AI_Agent_System/agents/` and root policies into `06_Execution_Plan/`; rewrite relative links. Merge the C15 durable-assignment/peer-inbox/round discipline without importing another product's environment, sessions or permissions. Existing C1/C6/C8 review defaults remain unless the target founder explicitly adopts a consistent replacement. The optional single-review example is not enabled by migration.
6. Keep only inactive examples in source distribution. Do not copy live config, `var/`, owner IDs, socket paths, profile directories, active waves, native ACKs, mailbox grants, run evidence or another project's topology. Profile overrides are fresh-session-only and explicit; unspecified profiles inherit. The new transport's current tested reference topology is three threads; adapt/test selectors for other thread counts.
7. Run isolated automation, file-signal, MCP/editor and metadata checks relevant to changed surfaces. Validate the installed paths and startup/preview behavior without activating agents. Mode scripts must refuse a conflicting active Mode. `automode status` reports controller state plus the same process Mode as `initiate_automation --status`. No native wake/authentication claim follows from mocked tests.
8. Only after accepted migration, record its source/installed changes, current framework version, validations, deviations and immutable receipt in the target. A partial migration keeps its previous accepted version. Updating the canonical framework never marks another product migrated.

Choosing Ultimate Auto, creating a live relay config, binding existing owners, starting automation, first waking each owner, fresh worker dispatch and every protected operation remain distinct project-authorized actions. Preserve original wave deadlines, finite budgets and the receipt distinction between proposed, recorded, delivered, consumed and accepted.

Rollback restores reviewed source/config paths at an authorized idle checkpoint, retaining owner claims, historical receipts and later accepted work. Do not kill sessions, delete runtime evidence or renew a deadline automatically.
