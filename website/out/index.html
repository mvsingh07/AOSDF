01 — The problem

AI-assisted development breaks in two places, not one.

Most tooling only tries to fix the first. Orchestrum fixes both, using the same discipline.

A sprint without discipline

Day 1Agent invents its own schema — nobody agreed on the data model first
Day 3Security gets reviewed after the code is already merged, if at all
Day 5Redis goes in for caching — the "why" lives in someone's memory, nowhere else
Day 90A status meeting exists just to reconcile three different tracking docs
Interview"I used Redis" is the entire answer — the trade-off is gone

A sprint on Orchestrum

Day 1Contract and schema exist before a single implementation task is assigned
Day 3captain_agent won't lock the plan until FRD coverage and the threat model both check out
Day 5ADR-004 ships with the caching decision — and its concept tag — in the same commit
Day 90execution_plan.md is still the only status record anyone opens
InterviewYou walk through the real trade-off from memory, roadmap open on the second monitor

The build problem

Agents invent their own architecture, skip security because it's "just an internal tool," and ship features before the data model is agreed on.

  • No contract, no code — API shape and schema exist before implementation
  • Security review gates execution, not a suggestion after the fact
  • One status column is the truth — no drifting tracking boards

The memory problem

Startup developers move too fast to write down what they learned — so six months of real, defensible engineering becomes unexplainable at the one moment it matters most: the interview.

  • Every ADR already contains an interview answer — it's just never tagged
  • No second authoring task, no separate content to maintain
  • Rendered locally, in your own sequence — build order or learn order

02 — The insight

Every decision your agents make is already an interview answer.

The raw material already exists. It just needs to be tagged and sequenced — not written twice.

An ADR is already "here's a decision, here's why, here's what we rejected" — that's a system-design answer, word for word. A threat model is already a structured account of what could go wrong and how the system defends against it. A domain model already defines entities, invariants, and state machines.

None of that needs to be authored a second time. It needs five extra lines of frontmatter on a document an agent was already writing — filled in by the same agent, in the same session, because it already has full context of the decision it just made.

03_System_Design/003_orders_module/decisions/ADR-004-cache-layer.md
---
concepts: [caching-strategies, cache-invalidation, redis-internals]
concept_category: Distributed Systems
difficulty: intermediate
prerequisites: [http-caching-basics]
interview_angle: why write-through over write-back here
built_at: M2-T4
---
Same session
$ architect_agent — task M2-T4

Writing the ADR for the Order Service's caching layer. Decision, context, alternatives, consequences — the usual shape.

Five extra lines
concepts, category, difficulty, interview_angle

The frontmatter block goes on top of the same file. Nothing new to create, nowhere new to put it.

Weeks later, human-triggered
$ Learn: rebuild

concept_indexer_agent scans the whole tree, resolves prerequisites, joins built_at against execution_plan.md.

47 concepts indexed
Night before an interview
$ Learn: open

render/index.html opens locally. Switch to Learn Order, filter to Distributed Systems, step through.

03 — The system

One discipline, applied to building, shipping, and remembering.

Each pillar extends the same non-negotiable core — traceability, human approval gates, and exactly one source of truth.

Structured Build Pipeline

Phase → Milestone → Task → Subtask, with an agent for each stage: captain_agent plans, commander_agent delegates, execution_agent/validator_agent close the loop. Every task maps to at least one FRD requirement — unmapped work is a logged gap, not a silent miss.

execution_plan.md · single status record

IDE-Native Workflow

Work from VSCode and Claude Code — slash commands, subagents, and an MCP layer that reads and writes the same markdown files a human would. Milestones mirror onto Jira or Notion using the Epic → Story → Sub-task chronology teams already understand, synced only when you say so.

Track E · human-triggered sync

Personalized Learning Roadmap

The same ADR your agent writes to justify a caching layer already tags the concept, category, and interview angle. A read-only indexer turns your whole project into a sequenced, browsable roadmap — no separate content to author, ever.

Track L · purely local · zero dependency

From a product idea to a working system — with a paper trail

Minimal human intervention after the plan locks. You approve at milestone boundaries, not at every keystroke.

Meet the roster

Ten agents, each with one job and a fixed permission set — nothing runs outside what's written here.

WI

workflow_initiator

Checks every required document exists before anything else is allowed to run.

CA

captain_agent

Reads 00–05, generates the execution plan, validates full FRD coverage.

CM

commander_agent

Delegates the next planned task each session — one task per cycle, no exceptions.

EV

execution / validator

Builds and reviews the work, then closes the loop on the status column.

RR

research_and_refine

Called in for R&D-heavy tasks before implementation is allowed to start.

AD

addendum_agent

Handles post-baseline scope changes without touching the original plan.

TS

tracker_sync_agent

Mirrors milestones to Jira or Notion — only when a human runs the command.

CI

concept_indexer_agent

Builds the learning roadmap from tagged decisions. Read-only, always.

PA

principal_architect_agent

On-demand, human-invoked deep review against current external best practice. Writes redlines, never a silent rewrite.

Two of these agents also run in a stricter posture on request: superman_agent takes a discipline mode that forces every task through the full architect → reviewer → implementor → validator pipeline, with no reviewer skipped — normal mode keeps its original per-milestone behavior.

04 — The discipline

The core principles every pillar inherits.

Nothing added by later tracks is allowed to weaken these. New surfaces are clients of the files — never a second source of truth.

01

Security-first

The security document exists and is reviewed before any coding begins. No exceptions for "internal tools."

02

Contract-first

API contracts and schemas exist before implementation tasks are ever assigned.

05

Traceability

Every task → output → validation → status. Nothing exists outside the tracking system.

20

Portability-first

No provider SDK outside an adapter file — swapping infrastructure or a tracker never touches core logic.

22

One source of truth

execution_plan.md's Status column is the only task-status record — no separate tracking board, ever.

24

Human-triggered sync

No agent calls Jira, Notion, or the wiki on its own initiative. Sync happens when a human says so — every time.

26

Tooling is a client, never a store

The IDE extension, MCP layer, and every renderer read the same files — none of them introduce a parallel database.

28

Learning content is derived

The roadmap contains no original prose — every fact traces to a document that exists for its own reason.

29

Tagged at the moment of decision

The agent making the call writes the concept tag — never a separate authoring pass, never scheduled later.

Security & trust

Built for the questions a security review actually asks.

None of this is aspirational — it's the same set of constraints every pillar above is built on, restated for whoever has to sign off on adopting it.

Security review gates execution

The threat model is reviewed before implementation starts — not audited after the fact.

Local by default, hosting opt-in

The learning roadmap and framework docs render locally with no telemetry. A separate, opt-in hosted platform exists for teams who want a product's docs built and served centrally — it never runs unless you register a repo yourself.

git push stays human-only

No agent, hook, or IDE command has push access — that permission is outside every agent's tool set by design.

Planning artifacts stay out of source control

AOSDF/ and {project_name}-Documents/ are gitignored — decisions don't leak into repo history.

05 — Who it's for

Built for teams shipping fast — and for the engineer who built it.

For engineering teams

Ship with a paper trail stakeholders can read.

  • One execution plan, always current — no status meetings to reconcile it
  • Milestones mirror to Jira or Notion in the vocabulary PMs already use
  • Security and legal constraints are binding architecture inputs, not footnotes
  • New hires get a browsable framework docs site instead of six raw files
  • Swapping trackers is a config change, never a live migration

For solo builders & startup engineers

Never lose the thread of your own best work.

  • Every real trade-off you made becomes a tagged, teachable concept
  • Study in build order — how you actually shipped it — or fundamentals-first
  • Local by default, no telemetry — hosted docs are opt-in, not required
  • Walk into an interview able to defend the thing you actually built
  • Doubles as onboarding material the day you bring on a co-founder

06 — Questions

Answers before you have to ask.

The objections that come up first, from teams evaluating this and from developers deciding whether it's worth the setup.

Do I need Jira or Notion to use this?

No. Tracker sync is opt-in, asked once at setup and never revisited automatically. The framework runs entirely through markdown and chat with no tracker configured at all.

Does this lock me into Claude Code or VSCode?

No. It's a file-and-prompt framework at its core — the VSCode extension and Claude Code integration are additive tooling on top, not a requirement to get value from it.

What happens to my data?

Nothing leaves your machine by default. The learning roadmap and framework docs browser render locally, and tracker sync only ever fires when you run the command yourself.

Can I use just the Learning Roadmap, without the IDE tooling?

Yes — Track L has almost no dependency on Track E. It's a frontmatter convention, one indexer agent, and a static-site renderer. It ships and works on its own.

What if my Jira board is already organized differently?

tracker_config.md maps to your existing project key — the Epic → Story → Sub-task hierarchy adapts to however your board is already set up, it doesn't require restructuring it.

Is any part of this hosted, or does it cost anything to run?

No. Everything ships as files and agent prompts. The only external service involved is whichever tracker you optionally connect, and that's your existing Jira or Notion account.

What's the difference between Orchestrum and AOSDF?

Orchestrum is the product name for this site and its roadmap. AOSDF is the underlying open framework and spec it's built on — same system, two names for two audiences.

07 — Roadmap

Where the framework is headed.

Each track ships independently and stays backward compatible — nothing here requires a rewrite of a project already running on Orchestrum.

v1.1 – v1.9 Shipped

Foundations

Research-before-design, gap tracking, the captain/commander agent split, the LLM wiki context layer, and manual-action tracking.

v2.0 – v2.3 Shipped

Portability & per-module design

Abstraction interfaces for every infrastructure client, post-baseline addendums, and per-module NNN_<name>_module/ design folders.

v2.4 Shipped

Optional Jira board sync

Human-triggered, one-directional mirror of the execution plan onto a Jira board — the model Track E went on to generalize to Notion.

v2.5 – v3.0 Current

Track E — IDE & tracker integration

A VSCode extension (status bar, gaps/actions inbox, multi-root workspace support), native Claude Code subagents and hooks, an aosdf-mcp read/write layer, and a Jira-or-Notion tracker adapter. Internal-distribution only for now — run from source or install a built package, no public marketplace listing yet.

v2.5 Shipped

Track L — Learning Roadmap

The Concept Frontmatter Standard, concept_indexer_agent, and a self-contained Build Order / Learn Order renderer, with an editor command to open it in one click — ships independently of Track E.

v2.5 Shipped

Track P — Project Docs Site

A rendered, searchable documentation site for every product built on the framework — execution plan, milestones, module designs, and ADRs — with a one-click link out from the editor.

v3.0 Current

Track H — Hosted docs platform

Register a product's repo, get its docs built and hosted automatically — sign in, then build and view from the same dashboard.

v3.1 – v3.2 Shipped

Discipline, review depth & efficiency

An on-demand principal_architect_agent for external-informed re-review, a discipline mode for superman_agent that forces every task through a reviewer gate, a logged-and-stopped protocol for out-of-scope work discovered mid-task, and advisory model-tier and context-window compaction guidance.
